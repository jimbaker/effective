# --- why vendored, rather than pinned from the registry ---
#
# Upstream `TemplateParser.close` judges its own buffer BEFORE telling the parser that
# input has ended, and CPython 3.14.7 turned that into a false parse error on a
# well-formed template. 3.14.7 made `HTMLParser.feed` BATCH: input accumulates in
# `self._pending` and is only joined into `self.rawdata` and parsed once `_pending_len`
# reaches a threshold that doubles whenever a pass parses nothing — a fix for quadratic
# rescanning of an unterminated tag. tdom feeds one static or one placeholder at a time,
# which is exactly the access pattern that batching defers, so at close() the tail of the
# document is still in `_pending` and `rawdata` is truncated mid-attribute.
#
#   html(t'<g class="{k}"></g>')   # 3.14.5: <g class="x"></g>;  3.14.7: ValueError
#
# It took 15 tests here (graphlayout, dashboard, graphlayout_elkjs), deterministic over
# six hash seeds. It is NOT a t-string change: Lib/string/templatelib.py is byte-identical
# between 3.14.5 and 3.14.7.
#
# Upgrading is not the alternative. Upstream latest is 0.1.18 (2026-07-10) and its
# parser.py is byte-identical to 0.1.17's — 0.1.18 changes only processor.py and adds
# py.typed — so it fails identically. Nothing in the tracker mentions this; it is
# unreported, and the patch below is written to be sent upstream unchanged.

# --- the patch ---
#
# patches/0001-close-drain-before-judging.patch, and it is the WHOLE divergence:
# `pristine sdist + patch == infra/tdom` is checked, not asserted (see below).
#
# It adds `_drain_pending_feed()` and calls it first in `close()`. The drain parses the
# held-back input as MID-stream — goahead(0), not close()'s goahead(1) — which matters:
# the first attempt at this fix simply moved `super().close()` to the top of the method,
# and goahead(1) flushed unterminated constructs as TEXT. Three diagnostics changed and
# `html(t'<')` silently rendered `&lt;` instead of raising. Ordering was not the bug; the
# invariant was. The drain restores it: everything fed has been parsed, which is what
# `waiting_for_data()` has always assumed.
#
# A no-op before 3.14.7 — `_pending` does not exist there and `feed` parsed eagerly — so
# the same vendored tree serves both interpreters.
#
# Yes, it touches `_pending` / `_pending_len`, which are private. That is deliberate and
# is the narrower of the two evils here: the alternative is to change WHEN the diagnostics
# run, which changes what tdom reports for malformed input. If upstream would rather not
# reach into stdlib privates, the better long-term shape is for `feed_template` to build
# the sentinel-substituted string and feed it in ONE call, which sidesteps batching
# entirely and is faster; that is a larger change and is not what this patch does.

# --- acceptance, measured 2026-08-18 ---
#
# An eight-case probe (five malformed templates, three well-formed) run four ways:
# unpatched/3.14.5 is the BASELINE, and patched/3.14.5, patched/3.14.7 all reproduce it
# case for case, message for message. Suites: `just check` 3761 passed / 3 skipped /
# 6 xfailed exit 0 on BOTH interpreters; `just pgt-test` 238 passed exit 0. The repo pin moved
# forward to 3.14.7 once this landed, so the vendored fix is what the gate runs on now — the
# 3.14.5 column is the regression check, not the shipping configuration.
#
# Re-run the probe when re-vendoring. A fix that makes the 15 pass while degrading what a
# malformed template reports is not a fix, and only the malformed half of the probe says so.
